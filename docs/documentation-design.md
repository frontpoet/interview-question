# 文档结构与整理规则（设计稿）

## 1. 内容模型

使用 UTF-8 Markdown、YAML 元数据、相对路径链接和 Git 管理。

| 对象 | 定义 | 存放位置 |
| --- | --- | --- |
| 标准题目 | 一个独立考察目标，附可独立阅读的简要回答 | `questions/`，一题一文件 |
| 知识点 | 一个可复用的概念或机制 | `knowledge/`，一个知识点一文件 |
| 原始问法 | 用户的具体表述，多个问法可对应一题 | 题目页“常见问法”；长记录可放 `inbox/` |
| 来源 | 题目出处或答案依据 | 对应条目的来源小节 |

题目写回答，知识点解释原理。同一知识点供多题引用，不为每个术语、问法或来源单独建页。

## 2. 目录与分类

```text
interview-question/
├── README.md                     # 项目说明、索引入口
├── docs/
│   └── documentation-design.md   # 本规范
├── inbox/                        # 可选：原始记录
│   └── YYYY-MM-DD-主题.md
├── questions/
│   ├── README.md                 # 题目总索引
│   └── operating-systems/
│       ├── README.md             # 分类索引
│       └── q-<标识>-<主题>.md
└── knowledge/
    ├── README.md                 # 知识点总索引
    └── operating-systems/
        ├── README.md             # 分类索引
        └── k-<标识>-<主题>.md
```

按需建目录和索引，不建空页面。题目和知识点共用以下主分类：

| 目录名 | 范围 |
| --- | --- |
| `computer-architecture` | 计算机组成、指令、缓存、存储层次 |
| `operating-systems` | 进程线程、调度、内存、文件系统 |
| `networks` | 网络分层、TCP/IP、HTTP、DNS |
| `data-structures-algorithms` | 数据结构、算法分析、编程题 |
| `databases` | SQL、索引、事务、数据库实现 |
| `programming-languages` | 语言语义、类型系统、运行时 |
| `software-engineering` | 设计原则、设计模式、测试、工程实践 |
| `distributed-systems` | 分布式协调、一致性、消息、分布式缓存 |
| `system-design` | 容量估算、架构设计、综合场景题 |
| `security` | 认证授权、漏洞、防护、密码学基础 |
| `frameworks-tools` | 框架、中间件用法、构建与开发工具 |

按主要考察目标或内容选择一个主分类，具体技术用标签表示。例如索引机制归入 `databases`，MySQL 作为标签。

目录用于导航，不表示概念继承。初期保持“内容类型 / 主分类 / 文件”三级结构；调整目录时修复全库链接。

## 3. 命名与元数据

文件名为 `<id>-<英文主题>.md`，使用小写英文、数字和连字符，例如 `q-a13f06b2-process-vs-thread.md`。

ID 由 `q-` 或 `k-` 加 8 位随机十六进制字符组成；创建时检查唯一性，之后不变。每页一个一级标题，日期为 `YYYY-MM-DD`。

| 字段 | 规则 |
| --- | --- |
| `id` | 必填，唯一且稳定 |
| `title` | 必填，规范名称，与一级标题一致 |
| `category` | 必填，与主分类目录名一致 |
| `tags` | 必填，字符串数组，可为空，复用已有标签 |
| `status` | 必填，见下表 |
| `created` / `updated` | 必填，创建日期 / 最近实质修改日期 |
| `type` | 题目必填：`concept`、`comparison`、`principle`、`scenario`、`coding`、`calculation` |
| `aliases` | 知识点可选，字符串数组，记录同义名称和缩写 |
| `scope` | 字符串数组，记录影响结论的技术、版本、环境和假设；有此类限制时必填 |
| `relations` | 可选，关系类型到目标 ID 数组的映射，见第 4 节 |

| 状态 | 含义 |
| --- | --- |
| `draft` | 有关键缺口、歧义或待核实结论 |
| `ready` | 内容完整，通过整理检查 |
| `reviewed` | 已经人工复核 |

AI 只能自行设置 `draft` 或 `ready`。AI 实质改写已复核内容后，应降为这两种状态之一。难度、频率和公司标签仅在有依据且有需求时添加。

- 知识点使用一个规范名称，例如“进程间通信”，别名可为 `IPC`。
- 缩写可能多义，须结合定义和上下文消歧；别名相同不代表同一知识点。
- 题目变体写入“常见问法”；相近概念用关系连接，不作为别名。
- 标签复用同一拼写，避免 `OS`、`os`、`操作系统` 并存为同义标签。
- `scope` 记录条目整体范围；局部限制写在结论旁。未填写不代表适用于所有版本。

## 4. 关系规则

关系只在起点条目的 `relations` 中维护，目标使用稳定 ID。

| 类型 | 方向与含义 |
| --- | --- |
| `examines` | 题目 → 直接考察的知识点 |
| `prerequisite` | 知识点 → 建议先学的知识点 |
| `follow_up_to` | 追问题目 → 原题目 |
| `confusable_with` | 知识点 ↔ 易混淆知识点 |

- `confusable_with` 为对称关系，只在 ID 字典序较小的一端记录。
- 目标必须存在，禁止自指和重复关系；`prerequisite` 禁止循环依赖。
- 前置关系表示学习顺序，不表示逻辑蕴含；不凭路径推导新关系或合并条目。
- 正文中的关系链接、反向链接和索引从元数据派生，不独立维护关系。初期由 AI 同步，后续可用脚本生成。
- 普通参考链接可直接写在正文，不必全部建模；同标签不自动建立关系。

以下仅演示格式，使用时替换为实际目标：

```yaml
relations:
  examines: [k-83e7c104]
  follow_up_to: [q-a13f06b2]
```

## 5. 页面模板

替换尖括号内容，删除空的可选小节。链接须指向实际文件，并与关系元数据一致。

### 题目

```markdown
---
id: q-<标识>
title: <标准题目>
category: <主分类>
tags: []
status: draft
type: concept
created: YYYY-MM-DD
updated: YYYY-MM-DD
relations:
  examines: [k-<已有知识点标识>]
---

# <标准题目>

## 题目

<完整问法，保留条件和限制。>

## 简要回答

<先给结论，再列必要要点。通常 3～6 点，适合约一分钟口述，以准确完整为先。>

## 相关知识点

- [<知识点>](../../knowledge/<分类>/<文件名>.md)：<需要掌握的内容>
```

可选小节：**常见问法、分析与边界、追问与关联题、题目来源、参考资料、待确认**。简短追问可在本页回答，有独立考察目标时拆题。

| 题型 | 必要内容 |
| --- | --- |
| 编程 `coding` | 输入输出、约束、示例、思路、代码、复杂度、边界情况 |
| 计算 `calculation` | 已知条件、单位、公式、步骤、结果 |
| 场景 `scenario` | 需求、假设、方案、取舍、适用边界，避免写成唯一答案 |
| 比较 `comparison` | 统一比较维度，按需用表格 |

### 知识点

```markdown
---
id: k-<标识>
title: <知识点名称>
category: <主分类>
tags: []
aliases: []
status: draft
created: YYYY-MM-DD
updated: YYYY-MM-DD
---

# <知识点名称>

## 核心概念

<定义及解决的问题。>

## 原理与机制

<关键过程或因果关系，按需附示例、代码或图。>

## 适用边界与易错点

<限制条件和易混淆概念。>

## 关联题目

- [<题目>](../../questions/<分类>/<文件名>.md)
```

可选小节：**前置知识、参考资料、待确认**。

知识点至少有定义和原理解释。优先复用或扩展已有页；无法可靠补齐时，在题目中标记待补充，省略对应关系和链接，不建空页。

## 6. 检索与合并

先查全库的标题、问法、别名、标签、正文和关系，再阅读候选条目全文。相似度只用于找候选，合并须核对**考察目标、适用条件、预期答案**。

| 情况 | 操作 |
| --- | --- |
| 目标、条件、答案一致 | 复用原题，仅补充有价值的新问法或来源 |
| 同一目标，新增细节 | 扩展答案或边界说明 |
| 相关但有独立考察目标 | 新建题目；属于追问时记录 `follow_up_to` |
| 条件变化导致答案变化 | 简短差异在原页分情况说明；需独立分析则拆题，正文注明区别 |
| 只有主题相同 | 分别收录，按需复用知识点 |
| 题意不明或结论冲突 | 保留原始描述或分歧，设为 `draft`，列出待确认项 |

“进程线程区别”与“进程和线程有什么不同”可合并；“线程切换开销为什么可能较小”另建追问。A 与 B 相似、B 与 C 相似，不能推出 A 与 C 应合并。

合并时保留正确细节、示例、来源及限制。无新信息不修改文件、不刷新日期。知识点合并另须核对定义和适用范围，不能只看名称。

合并已有文件时，选定主条目，迁入独有内容，重写关系目标、正文链接和索引。旧文件仅保留 `id`、`title`、`redirect_to: <主条目 ID>` 及正文迁移链接。迁移页免于普通模板要求，不进入索引，不含业务关系；目标必须是同类有效主条目，禁止循环或多级跳转。

## 7. 准确性与来源

- 分开写事实、假设和待确认项；不得将补充假设写成原题要求。
- 注明影响结论的版本、环境和约束。可按明确假设作答；无法确定则保持 `draft`。
- 题目来源只记录已提供的信息，不猜测公司、年份、岗位或频次。
- 答案依据写入“参考资料”，注明资料标题、链接及相关版本或章节；关键结论就近引用。
- 版本特性和不确定结论优先查官方文档、标准或原始论文；未查阅不称已核验。
- 外部内容用概括和链接引用，避免大段复制。面试记录不作为答案正确性的证明。
- 代码注明有影响的语言版本；执行后记录验证范围，未执行不写“测试通过”。
- 原始记录可存 `inbox/`，处理后标记已处理并链接目标题目。
- 所有入库内容去除无关个人信息、内部地址和密钥。

## 8. 整理与检查

每次按以下顺序处理：

1. 提取目标、条件和来源，拆开独立问题。
2. 检索候选，判断复用、扩展、新建或待确认。
3. 编辑题目和必要知识点，更新关系元数据。
4. 同步正文链接、反向链接及受影响索引。
5. 检查差异，返回文件链接、变更摘要和待确认项。

索引仅列规范标题、状态及题型（仅题目），每个主条目在所属分类中列一次。根 README 链接已存在的总索引，总索引链接分类索引。

完成前检查：

- ID 唯一，元数据合规，分类与路径一致。
- 关系类型、目标类型、方向和约束符合第 4 节。
- 链接可访问，派生内容与元数据一致，迁移引用已更新。
- 回答切题，与知识点一致；范围明确，关键缺口已标记。
- 无空页、虚构来源或无依据的“高频”“已验证”声明。
- 只修改本次题目及必要关联内容，保留已有有效信息。

结构检查不能证明答案正确。先用真实题目试行规则，再编写仓库 AI 指令和检查脚本；初期通过 Git 差异人工审查。
